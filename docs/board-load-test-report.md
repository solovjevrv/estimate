# Отчёт: нагрузочное тестирование досок (Epic 21.10)

**Дата:** 26.08.2026

**Цель:** доска с 50 одновременными участниками и не менее 1000 элементов (включая
стикеры и анимированные варианты) — без ошибок и в разумной латентности.

## Окружение

Локальная копия прод-сборки, не боевой сервер: `docker-compose.loadtest.yml` (тот же
подход, что и в `docs/load-test-report.md` для комнат) — тот же `apps/server/Dockerfile`,
что и на проде, отдельная БД и порты (`5433`/`3001`), изолированный Compose-проект
(`name: poker-loadtest`). `web`/nginx/certbot не поднимались — измерялся WS-шлюз и БД, не
раздача статики фронта.

- Сервер: 1 инстанс Node в контейнере, `NODE_ENV=production`, тот же образ, что деплоится
  на прод.
- БД: PostgreSQL 18, пул подключений приложения — `max: 30` (`apps/server/src/db/index.ts`).
- Хост: локальная машина разработчика — не референс по абсолютным цифрам CPU/RAM
  относительно прод-VPS, но валиден для проверки функциональной корректности и масштаба
  задержек.
- Инструмент: `apps/load-test/src/run-board.ts` + `board-scenario.ts` (21.10) — тот же
  `socket.io-client`-подход, что и у сценария комнат.

## Сценарий

Одна доска: 1 владелец (JWT-минтинг в обход OAuth, как в `apps/e2e`) + гости без аккаунта,
вошедшие по ссылке с правом правки (`shareRole: 'edit'`, тот же механизм, что у реальных
share-ссылок). До входа участников доска засеяна напрямую в БД 1000 элементами: 100
стикеров с `format: 'animated'`, 200 стикеров с `format: 'static'`, 700 обычных заметок —
имитация уже «нагруженной» реальной доски. Все 50 участников входят (`board:join`) почти
одновременно, затем волнами почти одновременно правят по одному элементу каждый
(`board:apply` → `item.patch`, джиттер 0–300мс — та же грубая имитация живых людей, что и
у сценария комнат).

Короткий прогон (5 волн) завершился за 2 секунды — сэмплер ресурсов (снимает раз в 500мс)
успел собрать только 1 замер, поэтому его CPU-цифра (92.3%) — не среднее по нагрузке, а
случайный пик в момент замера. Продлённый прогон (40 волн, 21 сэмпл) даёт представительную
картину: **CPU в среднем ~76%, пиково ~81% одного ядра** во время устойчивого потока
правок от 50 участников.

**Ни одной ошибки/таймаута ни в одном прогоне** (лимит ожидания ack в скрипте — 15с, реальный
максимум — 55мс). Задержки входа (снимок 1000+ элементов на каждого из 50 входящих)
стабильны между прогонами (~220мс p50, ~300-360мс p95) — не растут с длительностью
прогона, значит это не эффект накопления нагрузки, а постоянная стоимость сериализации/
передачи снимка такого размера.

## Вывод

**Цель выполнена с запасом.** 50 участников на доске с 1000+ элементами (включая
анимированные стикеры) отрабатывают без единой ошибки, с задержками в десятки-сотни
миллисекунд — некритично для совместного редактирования (не турн-based игра, где важны
единицы мс). CPU сервера (~76-81% одного ядра) уже заметно нагружен на этом одном
сценарии — согласуется с уже известным выводом из `docs/load-test-report.md` (Epic 6.3):
узкое место — однопоточность Node (event loop), не БД (32 подключения из пула `max: 30`
близко к потолку пула при 50 одновременных участниках одной доски — стоит учитывать при
дальнейшем увеличении масштаба, вероятно потребуется поднять `max` пула или это же
станет поводом для 10.18, горизонтального масштабирования).

Задержка «правка → рассылка всем» (169-320мс) выше, чем «правка → ack» (8-55мс) — ack
относится к одному сокету, рассылка ждёт получения ВСЕМИ 50 участниками, поэтому включает
хвост самого медленного из 50 соединений; это ожидаемо и не сигнал проблемы.

## Как повторить

См. `apps/load-test/README.md`, раздел «Сценарий досок (21.10)». Для представительного
замера ресурсов (не 1-2 сэмпла) — задавать больше волн (`LOADTEST_BOARD_WAVES`), чтобы
прогон длился хотя бы 10+ секунд при интервале сэмплирования по умолчанию (500мс).

## Повторный прогон с голосованием точками (15.2) — 04.10.2026

**Зачем:** перед релизом 15.2 (с августа доска получила таймер, блокировки текста,
голосование и др.). Голосование — новый профиль нагрузки: каждая точка — транзакция с
`SELECT … FOR UPDATE` на строке голосования и **персональная** рассылка `board:voting`
каждому участнику (до завершения чужие голоса скрыты), т.е. N участников × K точек × N
получателей снимков за раунд.

**Сценарий:** тот же, что выше (50 участников, 1000 элементов, 40 волн правок), плюс 5
раундов голосования: владелец запускает (вся доска, 3 точки на человека, на элемент — без
ограничения), все 50 почти одновременно ставят по 3 точки (джиттер 0–300мс перед каждой),
владелец завершает. Ack на точку уходит **после** персональной рассылки всем — поэтому
«точка → ack» включает её стоимость.

| Метрика (продлённый прогон, 40 волн + 5 раундов) | p50 / p95 / max      |
| ------------------------------------------------ | -------------------- |
| Старт голосования → снимок у всех 50             | 3 / 4 / 4 мс         |
| Точка → ack (750 точек)                          | 4 / 11 / 18 мс       |
| Раунд → у всех «проголосовали 50 из 50»          | 795 / 856 / 856 мс ¹ |
| Завершение → итоги с авторами у всех 50          | 15 / 20 / 20 мс      |
| Снимков `board:voting` на участника за раунд     | 152 (150 точек + 2)  |
| Ошибок                                           | 0                    |

¹ Почти целиком — джиттер сценария (3 клика × до 300мс), а не сервер.

**Регрессии правок нет.** Абсолютные цифры правок и входа на этой машине сегодня выше
августовских (JOIN p50 ~450 мс, правка → ack p50 ~47 мс), поэтому тот же профиль (40 волн,
без голосования) прогнан на трёх сборках в одном окружении:

| Сборка                  | JOIN p50/p95 | Правка → ack p50/p95 | Правка → рассылка p50/p95 |
| ----------------------- | ------------ | -------------------- | ------------------------- |
| `07145b3` (отчёт 26.08) | 410 / 614 мс | 61 / 147 мс          | 243 / 382 мс              |
| `v1.5.0`                | 541 / 603 мс | 55 / 133 мс          | 238 / 411 мс              |
| `dev` с 15.2            | 449 / 549 мс | 47 / 118 мс          | 215 / 371 мс              |

Августовский код в сегодняшнем окружении даёт те же цифры — разница с таблицей выше
объясняется хостом/Docker, а не кодом. Подключений к БД теперь до 52 — пул приложения с тех
пор поднят до `max: 50`.

**Вывод:** голосование точками на 50 участниках нагрузку не меняет — точка обходится в
единицы миллисекунд даже с персональной рассылкой на всех; склеивать рассылку
(coalescing) не нужно. Узкое место по-прежнему CPU одного процесса Node на потоке правок.
