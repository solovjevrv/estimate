# Исследование: импорт досок из Miro (Epic 22.1)

**Дата:** 27.08.2026

**Вопрос:** насколько применим импорт досок Miro в Estimate — что матчится с текущими типами
`BoardItem`/`BoardEdge`, а что нет, и что делать с непокрытыми объектами.

**Источники:** официальная документация Miro Developer Platform (`developers.miro.com`),
Miro Help Center, форум разработчиков Miro. Miro не публикует единый файл-экспорт доски,
который можно скачать и распарсить локально — единственный практический путь импорта
стороннего приложения — это её REST API v2 через OAuth-приложение.

## Вывод коротко

Технически применимо для MVP: **sticky note, shape, text, image, frame, connector, group** —
эти типы покрывают подавляющее большинство реальных досок и матчатся с нашей моделью с
приемлемыми потерями точности (цвет стикера — из фиксированной палитры Miro, не hex;
геометрия связи — по anchor-точкам, не по нашей модели floating edge). Не матчится вообще:
**card, app_card, document, embed, mindmap, tag** — для них нужно решение по каждому типу
(см. ниже), большая часть реальных досок использует их существенно реже базовых фигур/стикеров.

Экспорт доски целиком через специальный **Board Export API** для этой задачи не подходит —
он доступен только на Enterprise-плане Miro (через eDiscovery) и отдаёт SVG/PDF + метаданные,
не структурированный JSON объектов, пригодный для реконструкции элементов. Импорт нужно строить
на обычном REST API v2 (`GET /v2/boards/{id}/items` и per-type-эндпоинты), доступном любому
OAuth-приложению со scope `boards:read` — без ограничения по плану аккаунта пользователя.

## Как технически выглядел бы импорт

1. **Регистрация Estimate как Miro-приложения** (developers.miro.com) — client id/secret,
   redirect URI, запрашиваемый scope `boards:read` (для MVP только чтение — запись не нужна).
2. **OAuth 2.0 Authorization Code flow** — пользователь у нас на странице «Импорт из Miro»
   авторизуется у Miro, соглашается на доступ к своим доскам, мы получаем access/refresh token
   именно для этого пользователя (не сервисный токен на всё приложение).
3. **Список досок пользователя** — `GET /v2/boards` (тот же scope), пользователь выбирает,
   какую доску импортировать.
4. **Чтение элементов** — `GET /v2/boards/{id}/items` с пагинацией (курсор), либо по
   отдельным per-type-эндпоинтам (`/sticky_notes`, `/shapes`, `/texts`, `/images`, `/frames`,
   `/connectors`, ...) — итоговый список объектов на доске, включая позицию (x/y), геометрию
   (width/height/rotation), стиль и связь с родительским фреймом (`parent.id`).
5. **Маппинг** каждого объекта в `BoardOp[]` (`item.create`/`edge.create`) нашего протокола и
   применение одним батчем через существующий `applyBoardOp` — та же точка входа, что у
   copy/paste и дублирования (12.х), никакого нового серверного пути писать не нужно, кроме
   самого преобразования Miro JSON → `BoardItem`/`BoardEdge`.
6. **Лимит** `BOARD_MAX_ITEMS = 2000` уже есть в контракте — доску большего размера нужно либо
   обрезать с явным предупреждением пользователю, либо отказать целиком (решение продуктовое,
   не техническое).
7. **Rate limiting** у Miro — кредитная модель (не «X запросов в минуту»), с достаточным
   умолчальным лимитом на пользователя+приложение — для разовой ручной операции импорта одной
   доски (десятки-сотни объектов) не является практическим ограничением.

## Что предлагаю по непокрытым типам

Единообразный принцип вместо решения по каждому типу отдельно: **импорт — best-effort, не
1:1 репликация**. По итогу импорта показывать пользователю сводку: сколько объектов перенесено
как есть, сколько — с потерей точности (карточки → стикеры, неизвестные фигуры → прямоугольник),
сколько пропущено целиком (embed/document/tag/comments) с перечислением. Это ожидаемая практика
у сравнимых интеграций (аналогично тому, как экспорт/импорт между графическими редакторами
обычно предупреждает о потере несовместимых слоёв) — не блокер, а вопрос честной коммуникации
результата, а не попытка добиться невозможного 1:1.

## Что не оценивалось в этом заходе (для отдельного технического плана перед стартом реализации)

- Точная схема JSON per-type-эндпоинтов (нужна свежая сверка по официальному OpenAPI Miro на
  момент старта реализации — источники в этом отчёте достаточны для оценки применимости, но не
  для написания парсера без дополнительной проверки).
- Точный список именованных цветов палитры `sticky_note.style.fillColor` и таблица маппинга на
  `BOARD_COLOR_PALETTE`.
- UX выбора: импорт в новую доску целиком или вставка в существующую (ближе ко второму —
  переиспользует уже готовый путь `paste`/`duplicate`).
- Стоимость поддержки OAuth-приложения Miro (модерация листинга в Marketplace нужна только для
  публичного стороннего распространения; для использования только своими пользователями
  подходит непубличное/dev-приложение — уточнить у Miro условия на момент реализации).

## Рекомендация

Стоит делать, но не как первую задачу Epic 22 — самая тяжёлая по объёму работы (OAuth-интеграция,
маппинг множества типов, перезаливка картинок, отчёт по итогам импорта) и с наименьшей уверенностью
в оценке без дополнительного технического плана непосредственно перед стартом. Остальные три
задачи эпика (22.2–22.4) технически проще и не зависят от внешнего API — логично сделать их раньше.
