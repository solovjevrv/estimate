# Отчёт: расход ресурсов на анимированные Telegram-стикеры (Epic 21.7)

**Дата:** 25.08.2026

**Цель:** понять, не тормозит ли у пользователя доска с несколькими
одновременно анимированными (TGS/Lottie) стикерами, и сравнить два режима
рендера `lottie-web` — текущий `svg` и альтернативный `canvas`.

## Окружение

Локальный dev-стек (не прод-сборка): реальный сервер (`tsx watch`, :3000) + реальный
Postgres/MinIO в Docker + реальный Telegram Bot API для импорта пака. Браузер —
Chromium через Playwright, без троттлинга CPU. Хост — рабочая машина разработчика, не
референс по абсолютным цифрам относительно устройства реального пользователя (особенно
мобильного или бюджетного ноутбука) — валиден для сравнения между собой (baseline / svg
/ canvas), не как гарантия конкретных цифр «в проде».

**Сценарий — намеренно стресс-тест, не типичная нагрузка:** один и тот же реальный
анимированный стикер (пак `HotCherry`, импортирован через API) размножен на 50 позиций
одной доски напрямую в БД (без 50 живых скачиваний из Telegram — измеряется стоимость
рендера на клиенте, а не импорта). Обычная работа с доской вряд ли когда-либо покажет
50 одновременно видимых анимированных стикеров в кадре — это верхняя граница, «шторм
стикеров», а не средний случай.

**Метод замера:** Chrome DevTools Protocol, `Performance.getMetrics` (снятие метрик до
и после 5-секундного окна) + собственный счётчик FPS через `requestAnimationFrame` в
том же окне.

## Результаты

| Сценарий                                     | FPS  | CPU (avg за 5с) | Script  | Layout | Recalc Style | JS Heap   | DOM-узлов |
| -------------------------------------------- | ---- | --------------- | ------- | ------ | ------------ | --------- | --------- |
| Baseline (пустая доска)                      | 60.1 | 1.3%            | 9 мс    | 0 мс   | 0 мс         | 30.8 МиБ  | 765       |
| 50 стикеров, `renderer: 'svg'` (текущий код) | 60.2 | **90.6%**       | 1917 мс | 166 мс | 1615 мс      | 136.0 МиБ | 9476      |
| 50 стикеров, `renderer: 'canvas'`            | 60.2 | **58.1%**       | 1876 мс | 0 мс   | 0 мс         | 381.7 МиБ | 3027      |

(CPU/Script/Layout/Recalc — время за 5-секундное окно; для CPU это доля от одного ядра.)

## Наблюдения

- **FPS не проседает ни в одном сценарии** — счётчик кадров сам по себе очень лёгкий
  колбэк, поэтому 60fps здесь не означает «всё гладко» — реальный риск не в частоте
  кадров компоновщика, а в **занятости главного потока**: 90.6% на `svg` означает, что
  почти нет запаса для другой работы (перетаскивание карточки, обработка клика,
  открытие поповера) — на этой машине с быстрым CPU видимого лага не поймали, но на
  более слабом/тёплом устройстве (бюджетный ноутбук, телефон, фоновые вкладки) этот
  запас может кончиться и проявиться как рывки при взаимодействии, а не как «мигающая»
  анимация.
- **`svg`-рендерер тратит ~93% занятости главного потока на Script + Recalc Style +
  Layout** — ожидаемо: `lottie-web` в режиме `svg` на каждый кадр мутирует реальные DOM-
  узлы (path/shape на каждый слой каждого стикера), отсюда и 9476 DOM-узлов на 50
  стикеров (~190 узлов на стикер).
- **`canvas`-рендерер снижает CPU на ~36% относительно** (90.6% → 58.1%) и полностью
  убирает Layout/Recalc Style (рисование идёт в растровый буфер, а не в DOM) — DOM-узлов
  меньше в 3 раза.
- **Но `canvas` в этом замере потребил в ~2.8 раза больше JS Heap** (381.7 МиБ против
  136.0 МиБ) — не проверено дополнительно (не форсировали GC перед снятием метрики,
  возможна разница в моменте сборки мусора, а не только в реальном стабильном
  потреблении); если решим переключать рендерер — стоит перепроверить память отдельно,
  с принудительным GC и на более длинном окне.

## Вывод

Явного пожара нет: даже искусственный «шторм» из 50 одновременных анимаций держит
60fps на обычной машине разработчика. Но 90%+ постоянной загрузки одного ядра CPU на
`svg`-рендере — это **известный потолок масштабирования**, который стоит держать в
уме: он не блокирует релиз 21.7 (доски с таким количеством одновременных анимаций —
не типичный сценарий), но при жалобах на тормоза с анимированными стикерами в будущем
это первое, что стоит проверить.

**Решение (после дополнительного ресёрча):** вынесено в отдельную последующую
задачу — переключить `renderer` на `canvas` в `LottieSticker.vue` (быстрый
однострочный фикс, ощутимо снижает CPU и число DOM-узлов ценой роста памяти,
которую стоит перепроверить отдельно с принудительным GC) **плюс**
`IntersectionObserver`-пауза анимации вне видимой области экрана (стандартный
браузерный API — тот же приём, что у ленивой загрузки картинок; работает
корректно и с CSS-transform-панорамированием Vue Flow, без кастомного `root`).
Вместе эти два пункта не только снижают CPU на месте, но и делают «шторм»
из N одновременных анимаций самоограничивающимся: реально крутится ровно
столько, сколько видно на экране, а не сколько лежит на доске.

Рассмотренный, но отклонённый на этом этапе вариант — миграция на
`@lottiefiles/dotlottie-web` (Rust+WASM, режим `DotLottieWorker` рендерит в
`OffscreenCanvas` в отдельном Web Worker, полностью снимая работу с главного
потока). Технически это самый сильный вариант против конкуренции с
драгом/кликами, но цена высокая: новая зависимость, ~500 КБ WASM (по
умолчанию тянется с CDN LottieFiles — для самостоятельного хостинга нужна
отдельная настройка), другое API, больше тестирования. Не оправдано при
текущей серьёзности проблемы (60fps не проседал даже в стресс-сценарии) —
держим в бэклоге на случай появления сценария с реально массовыми
одновременными анимациями (например, взрыв реакций-стикеров у всей команды).

## Как повторить

Скретч-тест на Playwright (`apps/e2e/tests/zzz-scratch-perf-lottie.spec.ts`, не
закоммичен — одноразовый спайк): создаёт пользователя, импортирует реальный
анимированный Telegram-пак через `POST /api/sticker-packs/personal/import`, вставляет
50 `board_items` напрямую в БД со ссылкой на один и тот же стикер, открывает доску в
браузере и снимает `Performance.getMetrics` + свой FPS-счётчик через CDP. Для сравнения
рендереров — временно поменять `renderer: 'svg'` на `renderer: 'canvas'` в
`apps/web/src/components/board/LottieSticker.vue`, дать Vite HMR подхватить изменение,
прогнать тест повторно.
