# Отчёт: нагрузочное тестирование (Epic 6, задача 6.3)

**Дата:** 31.07.2026
**Цель из бэклога:** не менее 15 голосующих в одном раунде и не менее 10 команд
(комнат), работающих одновременно.

## Окружение

Локальная копия прод-сборки, не боевой сервер: `docker-compose.loadtest.yml`
(корень репозитория) — тот же `apps/server/Dockerfile`, что и на проде, отдельная БД
и порты, изолированный Compose-проект (`name: poker-loadtest`). `web`/nginx/certbot не
поднимались — измерялся WS-шлюз и БД, не TLS-терминация и раздача статики фронта.

- Сервер: 1 инстанс Node в контейнере, `NODE_ENV=production`, тот же образ, что деплоится
  на прод.
- БД: PostgreSQL 18, пул подключений приложения — `max: 30` (`apps/server/src/db/index.ts`).
- Хост: локальная машина разработчика (не референс по абсолютным цифрам CPU/RAM
  относительно прод-VPS, но валиден для сравнения масштабов между собой и для проверки
  функциональной корректности под конкурентной нагрузкой).
- Инструмент: свой скрипт на `socket.io-client` (`apps/load-test`) — обоснование выбора
  вместо Artillery/k6 см. в истории задачи (нет поддерживаемого движка Socket.io ни в
  одном из них на момент проверки).

## Сценарий

На каждую комнату: один владелец (JWT-минтинг в обход OAuth, как в `apps/e2e`) + гости
без аккаунта (как в реальном входе по ссылке). На раунд: старт → голосование всех
участников почти одновременно (джиттер 0–300мс — грубая имитация того, что живые люди
не голосуют в один и тот же миллисекунд) → вскрытие карт → ожидание, что снимок с
результатом дошёл до всех гостей комнаты. Все комнаты и все раунды в них идут
**параллельно** — это стресс-сценарий («все проголосовали и скрам-мастер вскрыл
одновременно во всех командах»), а не усреднённая по времени нагрузка.

**Ни на одном масштабе — ни одной ошибки/таймаута** (лимит ожидания ack в скрипте — 10с,
на 100×25 максимум составил 2.07с). Целевой масштаб (10×15) отрабатывает практически
мгновенно и с большим запасом.

## Вывод: узкое место — не БД, а однопоточность Node

Число подключений к Postgres выходит на плато (~61–62) уже на масштабе ×3 и дальше **не
растёт** вместе с нагрузкой (×5 и ×10 показывают то же число), при этом задержка
продолжает расти нелинейно. Это значит, что пул подключений (`max: 30`) — не тот
ресурс, что упирается первым: даже съев его целиком плюс подключения сторонних
клиентов (сам скрипт нагрузки, сэмплер), система не деградирует по ошибкам, а просто
ставит работу в очередь. Загрузка CPU контейнера сервера при этом держится в районе
100–120% практически на всех масштабах ×3 и выше — то есть **упирается один процесс
Node в одно ядро** (event loop), а не БД и не память (память выросла всего вдвое, до
334 МиБ, на 17-кратном по сокетам масштабе).

Это количественно подтверждает уже известный пункт бэклога **7.12** («рассылки живут
в памяти одного процесса, при горизонтальном масштабировании нужен общий адаптер
Redis») — реальный путь поднять пропускную способность выше нынешнего запаса не
«докрутить пул БД», а несколько инстансов Node за общим Redis-адаптером Socket.io.
Приоритет 7.12 менять не нужно (см. пункт: «прод сейчас один инстанс») — но при
кратном росте реального числа команд это будет первое, что стоит сделать.

## Итог по цели 6.3

**Требование выполнено с большим запасом.** На заявленном минимуме (10 команд × 15
голосующих) сервис отвечает за единицы миллисекунд. Функциональная корректность
(отсутствие ошибок/расхождений состояния) подтверждена вплоть до 2500 одновременных
сокетов — на порядок выше требования. Деградация с ростом масштаба — это рост
задержки, а не поломка: полезная нагрузка не резалась, партии не расходились между
участниками (снимок «вскрыто» доходил до всех гостей даже на максимальном масштабе).

## Как повторить

См. `apps/load-test/README.md` — там же описан один найденный по ходу инцидент
инструментария (коллизия имени Compose-проекта с dev-стеком, устранена явным `name:` в
`docker-compose.loadtest.yml`; данные не пострадали) для тех, кто будет менять этот
файл в будущем.
