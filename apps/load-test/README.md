# Нагрузочное тестирование (6.3)

Проверяет цель из бэклога: не менее 15 голосующих в одном раунде и не менее 10 команд
(комнат), работающих одновременно. Гоняется вручную по мере необходимости, не часть CI.

## Окружение — локальная копия прод-сборки, не боевой сервер

Прогон поднимает `docker-compose.loadtest.yml` (корень репозитория) — тот же
`apps/server/Dockerfile`, что и на проде, но с отдельной БД и отдельными портами
(`5433`/`3001`). Реальный прод-VPS и его данные не трогаются вообще. `web`/nginx/certbot
намеренно не подняты: цель прогона — WS-шлюз и БД под нагрузкой, а не TLS-терминация и
раздача статики фронта — этот слой в замер не входит, см. `docs/load-test-report.md`.

**Важно:** в файле явно задано `name: estimate-loadtest` и сервисы названы `loadtest-*` —
без этого Compose в одной директории с основным `docker-compose.yml` считает одноимённые
сервисы (`postgres`) одним и тем же и может пересоздать/снести dev-контейнер вместо
своего собственного (см. комментарий в самом файле и `PROGRESS_ARCHIVE.md`, 6.3 — так и
случилось при первом прогоне). Не убирайте `name:` при правках файла.

## Аутентификация

Как и в `apps/e2e`: владельцы комнат — реальные строки в БД (`UsersRepository.upsertFromOAuth`),
их сессии — JWT, выпущенный напрямую `TokenService` тем же `JWT_SECRET`, что и у поднятого
сервера (в обход настоящего OAuth). Участники комнат — гости без аккаунта, как и в реальном
сценарии входа по ссылке.

## Запуск

```bash
# 1. Поднять стек (нужен JWT_SECRET ≥32 символов — любой, только для прогона)
LOADTEST_JWT_SECRET=$(openssl rand -base64 48) \
  docker compose -f docker-compose.loadtest.yml up -d --build

# 2. Накатить миграции на чистую БД прогона
docker compose -f docker-compose.loadtest.yml run --rm loadtest-server node dist/db/migrate.cjs

# 3. Запустить нагрузку (значения по умолчанию — 10 комнат × 15 участников × 5 раундов)
JWT_SECRET=<тот же LOADTEST_JWT_SECRET> \
DATABASE_URL=postgres://loadtest:loadtest@localhost:5433/loadtest \
  pnpm --filter @estimate/load-test start

# 4. Остановить и снести стек вместе с данными
docker compose -f docker-compose.loadtest.yml down -v
```

Параметры прогона — переменные окружения (`src/config.ts`):

| Переменная                       | По умолчанию               | Смысл                                        |
| -------------------------------- | -------------------------- | -------------------------------------------- |
| `LOADTEST_SERVER_ORIGIN`         | `http://localhost:3001`    | Куда бить REST/WS                            |
| `LOADTEST_ROOMS`                 | `10`                       | Комнат одновременно                          |
| `LOADTEST_PARTICIPANTS_PER_ROOM` | `15`                       | Участников на комнату (1 владелец + гости)   |
| `LOADTEST_ROUNDS_PER_ROOM`       | `5`                        | Раундов голосования на комнату               |
| `LOADTEST_VOTE_JITTER_MS`        | `300`                      | Разброс перед голосом — имитация живых людей |
| `LOADTEST_SERVER_CONTAINER`      | `estimate-server-loadtest` | Контейнер для `docker stats`                 |
| `LOADTEST_SAMPLE_INTERVAL_MS`    | `500`                      | Как часто снимать ресурсы (мс)               |

## Что измеряется

- Латентность «голос → ack» и «вскрытие → снимок дошёл до всех гостей комнаты»
  (p50/p95/max по всему прогону).
- Ошибки/таймауты WS-событий.
- CPU/память контейнера сервера (`docker stats`) и число подключений к БД
  (`pg_stat_activity`) — сэмплируются раз в 2 секунды на всём протяжении прогона.

## Очистка данных

Комнаты — с именем `LOADTEST `, пользователи — на домене `@loadtest.local`. Прогон
удаляет их сам в `finally` (в т.ч. при ошибке), не полагаясь на отдельный teardown —
проще, чем в `apps/e2e`, потому что стек и так одноразовый (`down -v` сносит БД целиком).

## Сценарий досок (21.10)

Отдельный сценарий (не запускается вместе со сценарием комнат) — цель из бэклога: доска
с 50 одновременными участниками и не менее 1000 элементов, включая стикеры и
анимированные варианты. Проверяет то же, что и сценарий комнат, но для другого
WS-протокола (`board:join`/`board:apply`, дискретные операции, а не целиком `RoomState`)
и другого профиля нагрузки (одна большая доска с большим и разнородным JSON-контентом,
а не много изолированных маленьких комнат). Не измеряет клиентский рендер (нет реального
браузера, только `socket.io-client`) — для стоимости рендера анимированных стикеров на
клиенте см. отдельный perf-тест в `apps/e2e` (`pnpm --filter @estimate/e2e test:perf`,
`docs/sticker-animation-perf-report.md`).

Гоняется вручную при внедрении фич, способных повлиять на нагрузку WS-шлюза/БД досок
(изменение протокола `board:apply`, схемы `board_items`, прав доступа, кольцевого буфера
догона и т.п.) — не часть CI, как и сценарий комнат.

```bash
# Шаги 1-2 — как в сценарии комнат выше (поднять стек, накатить миграции)

JWT_SECRET=<тот же LOADTEST_JWT_SECRET> \
DATABASE_URL=postgres://loadtest:loadtest@localhost:5433/loadtest \
  pnpm --filter @estimate/load-test start:board

docker compose -f docker-compose.loadtest.yml down -v
```

| Переменная                              | По умолчанию | Смысл                                                   |
| --------------------------------------- | ------------ | ------------------------------------------------------- |
| `LOADTEST_BOARD_PARTICIPANTS`           | `50`         | Участников одной доски (1 владелец + гости)             |
| `LOADTEST_BOARD_ITEM_COUNT`             | `1000`       | Элементов на доске до старта (сеются напрямую в БД)     |
| `LOADTEST_BOARD_ANIMATED_STICKER_COUNT` | `100`        | Из них — стикеров с `format: 'animated'`                |
| `LOADTEST_BOARD_WAVES`                  | `5`          | Волн почти одновременных правок (по одной на участника) |
| `LOADTEST_EDIT_JITTER_MS`               | `300`        | Разброс перед правкой — имитация живых людей            |

Остальные переменные (`LOADTEST_SERVER_ORIGIN`, `LOADTEST_SERVER_CONTAINER`,
`LOADTEST_SAMPLE_INTERVAL_MS`) общие со сценарием комнат.

Что измеряется: латентность «вход на доску (JOIN) → снимок дошёл» (стоимость сериализации
и передачи снимка с 1000+ элементов на каждого из 50 входящих), «правка → ack» и «правка →
рассылка дошла до всех участников» (p50/p95/max), плюс те же CPU/память/подключения к БД,
что и в сценарии комнат. Доля стикеров с `format: 'animated'`/`'video'` в содержимом
элементов — не ссылки на реально существующие личные Telegram-паки (для сервера важен
только объём/состав JSON-payload'а, а не разрешимость файла в MinIO).

Очистка — по тому же принципу: доски с именем `LOADTEST `, пользователь на
`@loadtest.local`, удаляются в `finally`.
